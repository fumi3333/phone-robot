# phone-robot マッピング仕様書（シミュレーション → Flutter/Dart 移植用）

作成: 2026-10-30
対象: スマホを頭脳にした小型 RC カー「86」の室内マッピング機能
対応実装: `sim_mapping.py`（Python / numpy + Pillow、本書の参照実装）

本書は、シミュレーションで検証したマッピングの中核ロジック
（占有格子地図＋フロンティア探索）を、実機の Flutter/Dart
（ARCore）実装へ移植するための仕様である。アルゴリズムは移植先でも
同一とし、差し替えるのは「自己位置の出所」と「距離データの出所」だけ、
という設計にしてある。

---

## 1. 座標系・単位

| 項目 | 定義 |
|---|---|
| 単位 | メートル（m）、ラジアン（rad） |
| 世界座標 | 部屋の南西隅を原点 (0, 0)。x = 東（右）、y = 北（上） |
| 向き（heading） | 0 = +x（東）、反時計回りが正 |
| グリッド | セル一辺 0.05 m。部屋 6.0 m × 5.0 m → 120 列（x）× 100 行（y） |
| セル (row, col) | x ∈ [col*0.05, (col+1)*0.05)、y ∈ [row*0.05, (row+1)*0.05) |
| 配列の添字 | [row][col] = [y][x]。表示時は y 軸を上下反転する |

Dart 側でも同じ規約を使うこと。ARCore の座標系（右手系・y 上・
カメラ後方が +z）は異なるため、§5 の差し替えポイントで一度だけ
本座標系へ変換し、内部はすべて本規約で統一する。

## 2. データ構造

### 2.1 占有格子地図（OccupancyGrid）

```
logOdds : Float32List(GRID_H * GRID_W)   // 添字は row * GRID_W + col
```

- 各セルは「そのセルが障害物である確率」の対数オッズを保持する。
  - 0.0 = 未観測（未知）
  - 正 = 障害物らしい、負 = 空間らしい
- 分類（表示・カバー率用）: `logOdds > 0` → 壁、`logOdds < 0` → 空間、
  `logOdds == 0` → 未探索。
- 計画用「走行可能」の判定は分類より厳しくする:
  `logOdds <= -0.8`（PLAN_FREE_L）。理由は §6 の失敗事例参照。
- カバー率 = 一度でも更新されたセル数 / 全セル数。
  （箱の内部など観測不能なセルが含まれるため上限は 100% にならない。
  参照シミュレーションでは理論上限 ≒ 97.6%。）

Dart では `Float32List`（typed_data）でそのまま持てる。
120×100×4B = 48KB で、スマホ側でも問題ない。

### 2.2 自己位置（Pose）

```
class Pose { double x; double y; double heading; }  // m, m, rad
```

- 2 種類を使い分ける:
  - **真値に相当するものは実機には存在しない**。実機が持つのは
    ARCore の推定位置のみで、これがシミュレーションの
    「信じている位置（believed pose）」に対応する。
  - シミュレーションでは真値＋誤差で believed pose を作っている
    （§5）。

### 2.3 距離スキャン（Scan）

```
class Scan {
  Pose pose;              // スキャンした時点の believed pose
  Float32List ranges;     // N_RAYS 本、単位 m、無限遠 = 計測なし
}
```

- 前方向の扇形: 視野角 60°、レイ本数 21 本（参照実装）。
  実機では ToF 深度画像から等角度サンプリングして同じ形にする（§5.2）。
- 最大距離 5.0 m、最小距離 0.10 m。

## 3. アルゴリズム

### 3.1 地図の更新（ログオッズ）

スキャン1回につき:

1. 各レイについて、believed pose からレイを伸ばす。
2. 計測距離の手前（終端から 10 cm 手前まで）のセルに
   `L_FREE = -0.40` を加算する（同じスキャン内で重複加算しない）。
3. 命中したレイの終端セルに `L_OCC = +0.85` を加算する。
   同一セルが free と hit の両方に該当したら hit を優先する。
4. 全セルを `[-4.0, +4.0]` にクランプする。

### 3.2 フロンティア検出

- フロンティア = 「計画用に走行可能（logOdds <= -0.8）」かつ
  4 近傍のいずれかが未探索（logOdds == 0）のセル。
- 全セル走査で抽出する（12,000 セルなので毎回全走査で十分）。

### 3.3 経路計画（A*）

- 対象: 計画用走行可能セルのみ。8 近傍移動、斜めはコスト √2。
  斜め移動は両脇の直交セルが走行可能な場合のみ許可
  （角抜け防止）。
- ヒューリスティクス: octile 距離。
- 目標: フロンティア候補をユークリッド距離の近い順に試し、
  最初に経路が引けたものを採用する（上限 60 候補）。
- 到達したらその場で 360° 回転スキャン（30° × 12 方向）を行い、
  再計画する。

### 3.4 探索ループと終了条件

```
初期位置でスキャン + 回転スキャン
while カバー率 < 95% and 移動ステップ < 上限:
    フロンティアが無ければ終了
    A* で最寄りフロンティアへ移動（1セル進むごとにスキャン）
    到着したら回転スキャン
```

- 安全側の終了ガード（参照実装に入っている）: 「到達可能な
  フロンティアが無い」計画が 2 回連続したら、フロンティアが
  残っていても終了する。歪んだ地図ではスキャンの滲みで
  カバー率が微増し続けるため、このガードがないと探索が
  終わらないことがある（§6 の失敗事例とは別の、運用上の注意）。
- シミュレーションの「1 セル移動」は、実機では「経路上の次の
  ウェイポイントへの走行」に読み替える（§5.3）。
- 実機の終了条件は上限ステップではなく、時間・バッテリー・
  ユーザー停止を主とする（カバー率 95% は目安として併用）。

## 4. 主要パラメータ（参照実装の値）

| パラメータ | 値 | 意味 |
|---|---|---|
| CELL | 0.05 m | セル一辺 |
| GRID | 120 × 100 | 6.0 m × 5.0 m 用。実機では対象空間に合わせて変更可 |
| MAX_RANGE | 5.0 m | センサー最大距離（Depth API の最も正確な範囲の上限） |
| FOV | 60° | 深度カメラの扇形視野 |
| N_RAYS | 21 | 1 スキャンのレイ本数 |
| L_OCC / L_FREE | +0.85 / -0.40 | ログオッズ増分（占有を重く、空間を軽く） |
| L_CLAMP | ±4.0 | ログオッズの飽和 |
| PLAN_FREE_L | -0.8 | 計画用「走行可能」のしきい値 |
| FREE_MARGIN | 0.10 m | 終端手前で free 加算を止める安全マージン |
| TARGET_COVERAGE | 95% | 探索の終了目安 |

## 5. 実データへの差し替えポイント

### 5.1 自己位置 ← ARCore Motion Tracking

- シミュレーション: believed pose = 真値 + 誤差
  （通常モード: 位置 σ=0.02 m、向き σ=1.5° の都度ノイズ。
  ドリフトモード: 誤差がランダムウォークで累積 = 補正なしの
  自己位置推定の模倣）。
- 実機: ARCore のカメラポーズ（位置＋向き）を取得し、本書の
  座標系（部屋原点・y 北）へ変換して believed pose とする。
  変換はセッション開始時の初期位置・初期方位で決める。
- **注意**: ARCore の自己位置もドリフトする（走行距離の
  1〜5% が目安）。シミュレーションのドリフトモードが示す通り、
  補正なしでは壁が二重に描かれ地図が歪む。対策の第一候補は
  ToF の実測距離による位置補正（壁までの距離が地図と矛盾したら
  位置を寄せる）と、同じ場所に戻った際のループクロージャ
  （歪みの一括補正）。本仕様の範囲外だが、拡張点として
  Pose に「補正量」を差し込めるようにしておくこと。

### 5.2 距離 ← ToF / Depth API

- シミュレーション: 前方扇形レイキャスト（真値ジオメトリ＋
  距離ノイズ σ=0.03 m）。
- 実機: ARCore Depth API の深度画像（Note 10+ では ToF と
  融合される）を入力し、次の手順で Scan.ranges を作る:
  1. 深度画像の中央の帯（車両の進路高さに相当する行）を取り、
     水平方向に 21 点を等間隔サンプリングする。
  2. **生深度ではなく Raw Depth（信頼度付き）**を使い、
     信頼度の低い点は「計測なし（無限遠）」として扱う。
  3. 深度画像の画角と FOV 60° の対応を、機種ごとに
     キャリブレーション値として持つ（レンズ画角がレイ角度表を決める）。
- 白壁・暗所では深度が外れる前提で、「計測なし」を異常扱いせず
  スキャン更新をスキップできる作りにする（§3.1 は元々
  命中なしレイを free 加算のみに使える）。

### 5.3 移動 ← 実車の走行

- シミュレーション: セル間を直進する理想移動＋
  「占有セルへの進入は物理フェイルセーフで拒否され、
  強い占有証拠として地図に記録する」というモデル。
- 実機: A* の経路（セル列）をウェイポイント列に圧縮し、
  スマホ → USB シリアル → ESP32 → モータードライバへ
  操舵指令として送る。近接 ToF が閾値を切ったら経路の
  セルが地図上で空間でも即停止し、そのセルを占有として
  記録して再計画する（シミュレーションのフェイルセーフと
  同じ意味づけ）。
- 実機では車両の向きがセルの進路方向と一致しない時間がある。
  スキャンは「実際に深度カメラが向いている向き」で
  believed pose に記録すること（移動方向で代用しない）。

## 6. 参照シミュレーションで確認した失敗と対策（実装上の注意）

1. **障害物の表面を「空間」と誤判定して侵入する**
   - 原因: 距離ノイズで計測が長めに出ると、free 加算が障害物の
     表面セルまで食い込み、薄い free の証拠だけで計画が
     障害物にルートを引いた。
   - 対策: (a) free 加算は終端の 10 cm 手前で止める
     （FREE_MARGIN）。(b) 計画用しきい値を -0.8 にし、
     1 回の hit（+0.85）を打ち消すには複数回の free 観測を
     必須にする（PLAN_FREE_L）。実機でも両方を入れること。
2. **占有セルの中からスキャンすると自分を囲む壁ができる**
   - 1 の派生。車両が障害物の中にいると全方位が至近距離に
     なり、周囲が占有で固まって身動きが取れなくなる。
     侵入自体を防ぐのが先で、実機では近接フェイルセーフが
     これに当たる。
3. **補正なしの自己位置では地図が歪む**
   - ドリフトモード（`sim_mapping.py --drift`）で再現。
     結果は `run_drift_map.png` と `DRIFT_MEMO.md` を参照。

## 7. 既知の限界（シミュレーションが模倣していないもの）

- 車両の運動学（ステアリング方式、加減速、滑り）は未実装。
  実機はセル間を直進できないため、経路追従の誤差が地図の
  歪みとして現れる余地がある。
- 深度の外れ方（白壁・暗所・反射面での欠損）は模倣していない。
  ノイズは一様なガウスノイズのみ。
- 動く障害物（人・ペット）は未対応。占有格子は静的環境前提で、
  動体は「薄い占有の痕跡」として残る。
- 段差・階段・床材の違いは扱っていない（平面前提）。
- 回転スキャンは「その場で回転できる」前提。実機の RC カーは
  小回りが効くとは限らないため、実機では切り返し動作への
  読み替えが必要。
