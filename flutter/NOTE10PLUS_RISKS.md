# Note 10+ 実機リスク一覧（ソフト面）

対象機種を **Galaxy Note 10+** に固定した前提で、Flutter アプリ
（`app/`、実装済み）のソフト面のつまずきを洗い出したもの。

## 前提と優先度の付け方

- **対象個体**: 日本版 Note 10+（SC-01M / SCV45 等）を想定。日本版は
Snapdragon 855 版（後述 R8）。OS は Android 12（One UI 4.1）止まり。
- **最初の実機テストは自宅の室内**（通常の照明・生活空間）。
シミュレーションの部屋条件は 6 m × 5 m で、自宅のリビング相当。
- 各リスクに段階タグを付けた:
- **** 自宅テストで普通に当たるもの（優先度高）
- **** 夜間の廊下・施設環境に特有のもの（今は設計だけ意識）
- **** どちらの段階でも効くもの
- 深刻さは2分類: **止まる系**（走行不能・暴走・プロセス死）と
**精度が落ちる系**（地図の歪み・誤検出）。

## 第一段：自宅テストで当たるリスク

### R1. トラッキング喪失にドライバが気づかない（止まる系／暴走系）

- **何が起きるか**: 白壁や特徴の少ない方向を向いたとき、ARCore の
トラッキングが PAUSED になる。するとポーズ配信が止まるが、アプリ側は
**古いポーズを「現在位置」と信じて走り続ける**。最悪、壁に向かって
最大30秒（ウェイポイントのタイムアウト）進み続ける。
- **なぜ起きるか（コードの根拠）**:
- `ArCoreManager.kt` の `onFrame()` は `TrackingState.TRACKING` の
ときだけポーズを配信する。PAUSED では何も送らない＝Dart 側では
「止まっている」のか「配信が止まった」のか区別がつかない。
- `RealSession` は `trackingState` を保持するが、使うのは
`real_page.dart` の状態表示行（102行目）だけ。
**`RealDriver` はトラッキング状態を一切読んでいない**（grep で確認）。
- `RealDriver._pose` は `latestPose` を無条件に返し、**鮮度チェックが
どこにもない**。
- **なぜ Note 10+／自宅で起きうるか**: 自宅の壁は白く無地が多い。
トラッキングは映像の特徴点頼みなので、ToF があっても自己位置の方は
白壁で落ちうる（深度の信頼度が ToF で助かる話とは別問題）。
- **深刻さ**: 止まる系（暴走側）。安全の根幹。
- **対策（ソフトで可能）**:
1. ポーズにタイムスタンプを持たせ、ドライバ側で「○○ ms 以上新しい
ポーズが来ていなければ即停止＋待機」を入れる（鮮度ゲート）。
2. `trackingState!= TRACKING` の間は駆動コマンドを出さない。
3. Kotlin 側は PAUSED 遷移を即時に通知済みなので、受け側の配線だけで済む。
- **検証方法**: 実機なしでも、Dart 側はフェイクの PoseSource で
「配信停止→停止するか」を単体テストできる。白壁で実際に PAUSED に
なる頻度は実機が要る（自宅テストの最初の確認項目）。

### R2. 近接フェイルセーフが「データなし＝障害物なし」に倒れる（止まる系）

- **何が起きるか**: 深度ストリームが止まった／遅れた瞬間、近接停止が
無効化され、障害物があっても「無い」扱いで進む。
- **なぜ起きるか（コードの根拠）**: `real_driver.dart` の `_minRange` は
スキャンが新鮮（`ScanFeed.isFresh`、600 ms 以内）でないと null を返し、
`_proximityBlocked` は null を「塞がれていない」と解釈する。
つまりフェイルセーフが**フェイルオープン**（壊れたら開く側）になっている。
- **深刻さ**: 止まる系。R1 と組み合わさると「目も位置も無いまま進む」
状態がありうる。
- **対策（ソフトで可能）**: 駆動中は「新鮮なスキャンがある時だけ進む」
（フェイルクローズ）に反転する。静止中・回転スキャン中は現行の
扱いでよいので、状態で切り替える。
- **検証方法**: Dart のフェイク ScanFeed で単体テスト可能。実機不要。

### R3. USB 切断時に「進めない」を障害物として地図に書き込む（精度が落ちる系）

- **何が起きるか**: 走行中に USB が抜ける／ESP32 がリセットすると、
車はファーム側の 400 ms ウォッチドッグで止まる（ここは安全）。
しかしアプリは切断に気づかず、ウェイポイントのタイムアウト（30秒）
到達後に `_markBlockedAhead()` で**実在しない障害物を地図に記録**する。
以後の計画がその偽の壁を避け続ける。
- **なぜ起きるか（コードの根拠）**:
- `SerialManager.kt` は detach を検出して `disconnect()` するが、
**自動再接続はない**。Dart 側のリンク状態は "disconnected" になる。
- `RealDriver` は走行中にリンク状態を見ておらず、`_sendNorm` の
送信結果（Boolean）も確認していない。送れないコマンドを送り続ける。
- **深刻さ**: 精度が落ちる系（地図の汚染）。自宅テストではケーブルの
引っ掛け・コネクタの緩みで普通に起こる。
- **対策（ソフトで可能）**:
1. ドライバがリンク状態を監視し、切断したら即 `aborted` 扱いで
終了する（タイムアウト経由の `_markBlockedAhead` を踏ませない）。
2. `_markBlockedAhead` は「リンク正常＋ポーズ新鮮＋スキャン新鮮」の
ときだけ実行する。
3. 再接続は手動でよいが、UI に「切断された」ことを明示する。
- **検証方法**: Dart 側の状態遷移はフェイクでテスト可能。実機では
「走行中にケーブルを抜く」テストが確実（自宅で実施推奨）。

### R4. 画面消灯・プロセス終了でセッションが黙って死ぬ（止まる系）

- **何が起きるか**: 走行中に画面が消える（既定の画面タイムアウト）→
One UI の電池最適化でプロセスが凍結／終了 → ARCore ループと
シリアルが止まる。車はウォッチドッグで止まるが、アプリを再度開くと
状態表示は「センサー開始済み」のまま**中身が死んでいる**ことがある。
- **なぜ起きるか（コードの根拠）**:
- `AndroidManifest.xml` にフォアグラウンドサービスの宣言がなく、
`WAKE_LOCK` 権限もない。`MainActivity.kt` に画面常時点灯
（`FLAG_KEEP_SCREEN_ON`）の設定もない。Dart 側にも wakelock
相当の処理がない（grep で全て無しを確認）。
- ARCore セッションは Activity プロセス内の HandlerThread で
回しているため、プロセスごと死ぬと全部止まる。
- Dart 側に `AppLifecycleState` の監視がなく（grep で確認）、
復帰時にセッションの再確立をする処理がない。`RealSession` の
`sensorsOn` フラグは実態と乖離しうる。
- **なぜ Note 10+ で起きやすいか**: 前掲の通り、Samsung の
Android 11 以降の制限は「フォアグラウンドサービス＋ウェイクロック
でも止めうる」水準で、緩和策（One UI 6.0〜）はこの機種に来ない。
- **深刻さ**: 止まる系。自宅テストでも画面タイムアウトは普通に起きる。
- **対策（ソフトで可能な範囲）**:
1. まず画面常時点灯（`FLAG_KEEP_SCREEN_ON`）を入れる。これだけで
自宅テスト中の大半は防げる（車載中は画面を見続ける運用のため）。
2. Dart 側に「ストリーム無音検出」（ポーズ／深度／リンクの最終受信
時刻を監視し、黙ったら状態を落として再開始導線を出す）を入れる。
3. 端末設定の運用対策: 本アプリを「スリープしないアプリ」に登録し、
バッテリーを「制限なし」に、Device Care の自動最適化を切る。
※ アプリ側から強制はできない。手順書として残す対象。
4. 本格的なフォアグラウンドサービス化は後段でよい。その場合も
Android 12 の「バックグラウンドからの FGS 起動禁止」に触れない
よう、開始は必ず画面操作からにする（現行の開始フローは適合）。
- **検証方法**: 実機で「画面タイムアウトを30秒にして探索を開始し、
消灯後に何が起きるか」を自宅で確認できる。プロセス死の頻度自体は
実機の長時間放置が要る。

### R5. 深度の画角換算が近似のままで、地図が歪む（精度が落ちる系）

- **何が起きるか**: 21本レイの角度と深度画像の列の対応がずれ、
壁が実際より内側／外側に、あるいは斜めに記録される。6 m × 5 m の
部屋では数十 cm の歪みがそのまま計画の失敗（通れる所を通れない等）
につながる。
- **なぜ起きるか（コードの根拠）**: `ArCoreManager.computeRays()` は
テクスチャ側の内部パラメータ（`textureIntrinsics`）を深度画像の
解像度へ単純換算して列位置を決めている。コード内コメントにも
「近似。厳密には機種ごとのキャリブレーションが望ましい」とある。
Note 10+ は GPU テクスチャ解像度が 1080p/720p/480p の複数候補を
持ち（公式リスト）、ARCore の選択次第で換算の前提が変わる。
- **深刻さ**: 精度が落ちる系。止まりはしないが、地図の正しさ全体に効く。
- **対策（ソフトで可能）**:
1. 実機で深度画像の実サイズと内部パラメータをログに出し、換算が
合っているか一度だけ検証する（キャリブレーション手順）。
2. 既知の距離（壁から 1 m）に置いて中央レイの実測と一致を見る。
- **検証方法**: 実機が要る（机上の再計算だけでは確定しない）。
自宅の壁とメジャーでできる。自宅テスト初期の必須項目。

### R6. 深度画像の解像度前提とサンプリング量（精度・負荷の両方）

- **何が起きるか**: 深度画像は通常 約160×120（公式）。この前提では
中央帯 40〜60% は 24 行分しかなく、現行のサンプリング
（±2列 × 2行間引き）で1レイあたり約60点の中央値を取る設計は
妥当な範囲。逆に、もし実機の深度画像が大きい（最大 640×480 級）
場合、同じコードでサンプル数が約9倍になり、更新スレッドの
負荷が増える。
- **コードの現状**: `computeRays()` は実サイズを `depthImage.width/
height` から読むため**固定値の決め打ちはない**（ここは契約通り）。
サンプル間引き（行 `r += 2`）も入っている。
- **深刻さ**: 精度が落ちる系（小さい画像では1レイの根拠が薄くなり、
白壁＋遠距離では中央値が取れず「計測なし」が増える）。
- **対策**: 実機で実サイズをログ確認し、必要なら間引き率を
解像度連動にする。信頼度 128 の足切りは公式の目安と一致しており
変更不要。
- **検証方法**: 実機のログ確認のみ。自宅テストで R5 と同時に取れる。

### R7. フォーカス AUTO のハンティング（精度が落ちる系）

- **何が起きるか**: `ArCoreManager` は `Config.FocusMode.AUTO` を
固定で使う。自宅の照明でも、壁に近づいた／向きを変えた瞬間に
AF が迷うと映像が一瞬ぼやけ、トラッキング品質と Raw Depth の
信頼度が揺れる。
- **深刻さ**: 精度が落ちる系（悪条件で R1 の引き金になる）。
- **対策（ソフトで可能）**: FIXED との比較を実機で一度行い、
問題が出るなら設定を切り替える（1行の変更で済む）。
- **検証方法**: 実機のみ。自宅の通常照明で「壁に近づく→向きを変える」
動作の繰り返しで差を見る。

## 両方の段階で効くリスク

### R8. SoC の2系統（Exynos 版は別物として扱う）

- **事実**: Note 10+ には Snapdragon 855 版（米・中・日本）と
Exynos 9825 版（欧州等）があり、GPU も Adreno 640 と Mali-G76 で
別物。本人の日本版（SC-01M 等）は SD855 なので、**第一段では
この問題は存在しない**。
- **効いてくる場面**: 量産や中古調達で海外版を混ぜたとき。ARCore の
認定自体は機種名単位だが、推論性能（将来の VLM 等）と発熱特性は
SoC で変わるため、「Note 10+ なら同じ」とは言えなくなる。
- **対策**: 機種の最低ライン定義に「型番（SM-N975F 等）ではなく
SoC」まで含める。中古調達時のチェック項目にする。
- **検証方法**: 型番と SoC は端末情報で確認できる。実機テスト不要。

### R9. USB 権限と再接続の手作業（止まる系・小）

- **何が起きるか**: USB 権限は接続ごとに必要。アプリを手で開いて
から挿すと毎回ダイアログが出る。逆に、USB 接続イベント経由の
起動（マニフェストの `USB_DEVICE_ATTACHED` フィルタ＋
`device_filter.xml`、CH340 の VID/PID 登録済み）では、
「常時このアプリで開く」を選べば以後は自動で権限が付く。
- **コードの現状**: 権限要求フローは実装済み。detach 検出も実装済み。
ただし復帰は手動（R3 と一体で対処）。
- **深刻さ**: 止まる系（小）。運用で吸収できる。
- **対策**: 運用手順として「ケーブルを挿してアプリを起動する」
順番を固定し、初回に「常時開く」を選択する。
- **検証方法**: 実機で抜き差しを数回。第一段の R3 テストと同時実施。

### R10. Android 12 止まりであること自体（両方・低）

- **何が起きるか**: OS が上がらない＝今後の ARCore（Google Play
開発者サービス）の要求水準が上がったとき、この機種が取り残される
可能性がある。ただし現時点の ARCore 1.44（アプリ同梱指定）＋
Play 開発者サービスの組み合わせは Android 12 で動作する。
セキュリティ更新は 2023年8月で終了済みのため、業務用にネットへ
常時接続する運用は避ける（巡回データの扱いは別途設計）。
- **アプリ側の事情**: `targetSdk` は Flutter 側の既定値
（ツールチェーン Flutter 3.24.5 では API 34 相当）だが、実行時挙動は
端末 OS の Android 12（API 31）の規則に従う。
- **深刻さ**: 精度でも停止でもなく「将来の賞味期限」。第一段では無視可。
- **対策**: なし（設計で避ける＝この機種を開発・検証の基準機と割り切り、
製品側の最低ラインは別途引く。これまでの決定通り）。

## 後段：夜間・施設環境で効くリスク

### R11. 暗所でのトラッキング喪失（止まる系）

- 夜の廊下では映像特徴が減り、R1 と同じ PAUSED が頻発する。
ToF の深度は暗所でも出る（能動センサー）が、**自己位置の方が先に
死ぬ**構造は変わらない。R1 の対策（鮮度ゲート＋状態連動停止）が
そのまま前提条件になる。
- 検証: 自宅の照明を落とした部屋で代替確認はできる。本番相当の
暗さは施設でしか分からない。

### R12. 長時間巡回の熱（精度が落ちる系→止まる系）

- ARCore 公式も熱監視を推奨している通り、連続稼働で SoC が
スロットリングすると、フレーム処理が落ち、トラッキング品質と
深度の更新間隔（現行 150 ms 決め打ち）が崩れる。
- 現行コードに熱の監視はなく、深度間隔・制御周期（100 ms 固定）も
状況に連動しない。`ScanFeed.isFresh` の 600 ms しきい値との
兼ね合いで、熱で遅れたスキャンが「古い」と判定され、R2 の
フェイルオープン問題と重なる。
- 自宅テストの探索は最大8分で終わる設定（`explore` の
`maxDuration`）なので第一段では当たりにくい。施設巡回（数十分）
では本題になる。
- 対策（後段でよい）: `PowerManager#getCurrentThermalStatus()` を
見て、熱が高いときは深度間隔と走行速度を落とす／休止する。
logcat の "VIO frequency low" の有無も切り分けに使える（公式）。
- 検証: 実機で30分以上の連続稼働が要る。

### R13. 無人放置と Samsung の自動最適化・アプリの休眠（止まる系）

- Device Care の「自動最適化」による定期再起動や、使わない期間が
長いアプリのスリープ／ディープスリープ入りは、無人運用の前提を
崩す（再起動後は誰もアプリを開かない）。
- Android 12 の hibernation は、長期間未使用のアプリの権限を
自動で取り消す。自宅で毎日触る間は当たらない。
- 対策: 運用設計（自動起動の導線、定期的な人の確認）と端末設定の
セットで扱う。アプリ単体では完全には防げない、と正直に置く。

## 結論（要点だけ）

1. Note 10+ 自体の能力は足りている。Depth API＋ToF の公式対応、
SD855（日本版）、深度の信頼度足切り（128）や範囲（0.1〜5 m）は
公式の目安と一致している。**機種選定は正しい**。
2. 第一段の本当の敵は機種ではなく**コード側の「無音への弱さ」**:
ポーズの鮮度を見ない（R1）、フェイルセーフが開く側に倒れる（R2）、
切断を障害物と誤認する（R3）、画面消灯で黙って死ぬ（R4）。
どれもソフトで直せる。
3. R5 の画角キャリブレーションだけは実機の実測が要る。
自宅テストの最初の30分で終わる作業。
4. 夜間・長時間・無人の問題（R11〜R13）は後段でよい。ただし
R1 の対策が全ての前提になるので、そこだけは第一段で入れる。
