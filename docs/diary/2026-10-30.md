## ハードウェア部品の確定と選定理由の全記録（2026-10-30 確定）

最終的に以下の構成で購入・確定した。

### 1. 確定した購入品目
- **マイコン**: `ESP32-DevKitC Type-C`（1,299円・税込・送料無料）[Amazon B0HNDRRGVZ]
- **モータードライバ**: `2ch DCモータードライブ ミニモジュール MX1508（3個入）`（699円・税込・送料無料）[Amazon B083DT2DMV]
- **合計総額: 1,998円（税込・送料無料）**
- **手持ち流用（0円）**:
  - ケーブル: 手持ちの Anker 45W 付属 Type-C to C ケーブル（USB 2.0データ通信対応）
  - 配線: 車体内部のモーター線および導線のハンダ直結

---

### 2. 選定理由と意思決定のロジック（なぜこれにしたのか）

#### ① マイコン: Arduino Nano ではなく ESP32 を選んだ理由
- **実質差額が300円**: 当初検討したArduino Nano Type-C単品が999円、ESP32 Type-Cが1,299円であり、差額はわずか300円だった。
- **将来の無線化と資産性**: 300円の差でデュアルコア（240MHz）とWi-Fi/Bluetoothが手に入り、後から完全ワイヤレス操縦へ移行可能。
- **Freenove（1,880円）を見送った理由**: Freenove製はGPIO16にオンボードRGB LEDが接続されており、既存ファームウェア（GPIO16〜19制御）とピン衝突を起こすため、標準ピン配置のDevKitC互換機を選択した。

#### ② モータードライバ: 大型L298N ではなく MX1508 ミニモジュールを選んだ理由
- **電気効率の差（約25〜30%のエネルギー損失回避）**:
  古い大型L298Nはバイポーラトランジスタ構造のため、内部で約1.5V〜2.0Vの電圧降下（Vce sat）が発生する。7.2Vの充電池駆動では約2V（約28%）が熱として無駄に捨てられ、モーターには5V程度しか届かない。
  対してMX1508は低抵抗MOSFET構造のため電圧降下がほぼゼロで、電池の7.2Vがそのままモーターに届き、発熱も最小限でパワフルに走行できる。
- **車載スペースの余裕**:
  外形が約25mm×21mmと親指サイズで、1/16トヨタ86の車体内部の狭い隙間に干渉なく収まる。
- **ハンダ直結による耐振動性**:
  ラジコンは走行時の振動が激しいため、ジャンパーピンの抜き差しよりも、電線を基板スルーホールにハンダ直結する方が接触不良や脱落を防げて圧倒的に信頼性が高い。
- **コストと予備**:
  3個入り699円（1個あたり約233円）で最安であり、配線ミスでチップを焼いた場合も予備が2個あるためリカバリが可能。


## ミューズ（Claude）との自動運転・ソフトウェア設計の議論全記録（2026-10-30）

深夜から明け方にかけて、ミューズ（Claude）と徹底的に議論して固めた自動運転ソフト・実験方針の記録。

### 1. 余剰 Colab GPU（コンピュートユニット）の使い道と優先順位
車体と走行データがない現時点で、失効するGPU枠をどう活用するかの議論。
- **1位（最優先・土台）: 公開データセットによるEnd-to-Endモデル学習 ＋ TFLite変換パイプライン構築**
  - Donkey CarやUdacityの公開走行データ（画像＋操舵角ペア）を使い、MobileNet等の軽量CNNで学習を回す。
  - スマホ（Note 10+）で動くTFLite（FP16/INT8量子化）形式への書き出しとベンチマークを済ませる。実車完成後にハマる環境構築エラーを今潰せる。
- **2位: 単眼深度推定（Depth Anything V2 Small等）のスマホ向け軽量化**
  - カメラ1枚で障害物への接近を検知するモデルの検証。自動ブレーキに直結。
- **3位: シミュレータ走行（Gym-DonkeyCar / CARLA）**
  - 最もロマンはあるが、Donkeyのシミュレータは「コース走行」であって「部屋」ではないため、室内走行への転移確度が最も低く後回しに決定。

### 2. ミューズと合意した2つの重要留保事項
- **留保①: 深度の「何cm」に惑わされない（相対深度の理解）**
  - Depth Anything等の単眼深度推定が出すのは「相対的な奥行き（無次元スコア）」であり、絶対的なcm（メトリック距離）は出ない。
  - ただし「画面下部のスコアがしきい値を超えたら接近とみなして止まる」というブレーキ用途なら相対値で十分機能する。距離計としての過度な期待は避ける。
- **留保②: ノートブックの前処理の固定と「ステアリングのオンオフ対応」**
  - 実車データが来た時にやり直しにならないよう、画像の切り出し（天井カット等のROI）とリサイズ、正規化を先に固定する。
  - トイラジコンのステアリングはサーボによる角度制御ではなく、DCモーターを左右に振り切るオンオフ駆動。
  - 出力は「-1.0〜1.0 の連続値」で出しつつ、アプリ側で「-0.3未満なら左、0.3超なら右、間は直進」としきい値処理できる設計にしておく。

### 3. ログ収集の実務設計（動画ファイル ＋ コマンドCSV）
- スマホで毎秒30枚の静止画（JPEG）をバラバラに保存すると、ファイルIOのオーバーヘッドでスマホが発熱しコマ落ちする。
- **スマホのハードウェアエンコーダを使った1本の動画（MP4）＋ 時刻（ミリ秒）付き操作コマンドCSV** で保存するのが最軽量で後処理も楽。

### 4. 車体の「40MHz」確認とモーター直結の絶対的正当性
- 実機で「40MHz」の刻印を確認。赤外線ではなく電波ラジコンと確定。
- 40MHzをマイコンから吹くのは高周波発振回路・電波法の技適リスク・独自パルス解読が必要で極めて難関。
- モーターから出ている赤黒2本の線に直接Hブリッジ（MX1508）から電気を流す「モーター直結」が、最も単純で確実な正解ルートであることを確認。

## 徹底的な粗探しと改善（2026-10-30 実機前レビュー）

実機走行・データ収集で必ず詰まる4つの潜在的バグ・設計の穴を洗い出し、改修完了。

1. **【AI学習の致命傷回避】録画ストリームを「HUDキャンバス」から「カメラ生映像」へ完全分離**:
   - `canvas.captureStream(30)` のままでは、MediaPipeの顔認識ボックスやテスラ風グリッド線、テキストが動画に焼き込まれ、AIがそれを特徴量として誤学習する致命的な問題があった。
   - `video.srcObject` から直接ストリームを取得し、装飾のない純粋なカメラ生映像（Raw Image）だけをデータセットとして保存するように修正。
2. **【走行停止バグ解消】手動ボタン長押し時の連続コマンド送信（100msインターバル）**:
   - ESP32の400msウォッチドッグに対し、ボタン押下時に1回しかコマンドが送られず、0.4秒後に車が勝手に止まる問題を解消。
   - ボタンを押している間は100ms間隔でコマンドを連続送信し、指を離した瞬間に停止するロジックを実装。
3. **【暴走防止ガード】タッチ外れ時の安全停止（touchcancel / window mouseup）**:
   - スマホ画面上で指がボタン外に滑った場合に `sendCommand(0, 0)` が漏れて暴走する危険を防止するため、`touchcancel` および `mouseleave` を確実にハンドリング。
4. **【ファームウェアの息継ぎ解消】Arduino Serial.setTimeout(15) の追加**:
   - `Serial.parseInt()` のデフォルト1,000ms（1秒）ブロッキングにより、わずかな通信遅れで400msウォッチドッグが誤作動して走行がガクつく問題を防止。タイムアウトを15msに設定。
5. **【配信環境の整合】ルート `index.html` と `web/index.html` の完全同期**:
   - GitHub Pagesの配信ルート設定による表示ズレを防ぐため、常に最新版を双方に反映。
